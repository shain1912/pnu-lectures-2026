뷰 행렬 — 카메라 이동의 실제 의미

\[ V = (\text{카메라의 월드 변환})^{-1} \]

GPU에는 "카메라"라는 물건이 없음 → 카메라는 항상 원점에서 −Z 방향을 본다고 가정 → 그래서 카메라를 움직이는 대신 세상 전체를 반대로 이동 (위 식의 역행렬 = 되돌리는 변환)

손계산 · 카메라 위치 (0, 0, 5)
→ 뷰 행렬 = 세상 전체를 (0, 0, −5) 이동
→ 월드 원점의 상자는 뷰 공간에서 \( z=-5 \)
= "카메라 정면 5m 앞"

뷰 행렬 = 고정 카메라 앞에서 무대 세트를 미는 촬영 · 카메라는 삼각대에 고정, 대신 세트 전체를 반대 방향으로 밀어 옮김 · 찍힌 화면은 카메라를 움직인 것과 똑같음 · 기차 창밖 풍경이 뒤로 흘러가는 느낌과 같은 원리

11주차 연결 : VR에서 카메라 Transform 직접 조작 금지의 근거

- 무대 세트 비유 : "영화 촬영장에서 카메라를 못 움직이게 묶어 두고, 대신 세트를 통째로 밀면 화면은 똑같이 나온다. GPU가 바로 이렇게 한다" - 손계산 : 카메라를 +Z로 5 → 세상을 −Z로 5 → 원점 물체가 카메라 앞 5m

뷰포트 — 마지막 확대 단계

뷰포트(viewport) : 그림이 실제로 찍힐 화면 속 직사각형 영역 · 보통 화면 전체

\[ x_{screen} = (x_{ndc}+1)\cdot\tfrac{W}{2} \] \[ y_{screen} = (y_{ndc}+1)\cdot\tfrac{H}{2} \]

W·H = 뷰포트의 가로·세로 픽셀 수 · NDC(−1~+1)에는 해상도 정보가 없음 → 해상도는 마지막에 곱해서 반영

손계산 · \( x_{ndc}=0.5 \), 1920 폭 화면
\( (0.5+1)\times 960 = 1440 \) 번째 픽셀
같은 점이 4K(3840 폭)에서는 2880 번째
→ 둘 다 화면 폭의 75% 지점 · 구도 동일

뷰포트를 화면 왼쪽 절반으로 지정 → 그 절반 안에 −1~+1 배치 · VR의 좌·우 눈이 이 방식으로 한 장의 그림을 나눠 씀

NDC = "가로 몇 %, 세로 몇 %"로 적은 사진 설계도 · 뷰포트 = 인화 · 같은 설계도를 엽서로 뽑든 포스터로 뽑든 구도는 그대로, 점의 개수만 다름

- 사진 인화 비유 : 설계도에는 "왼쪽에서 75% 지점에 사람" 처럼 비율만 적혀 있음 → 인화지 크기에 맞춰 실제 위치 결정 - VR 연결 : 한 장의 인화지를 반으로 접어 왼쪽엔 왼눈, 오른쪽엔 오른눈 그림

원근의 원리 — 닮은꼴 삼각형

눈에서 화면(near 평면)까지 거리 \( n \) · 물체까지 거리 \( -z \)
(카메라가 −Z를 보므로 앞쪽 물체는 \( z \lt 0 \))

\[ \frac{x'}{x} = \frac{n}{-z} \;\Rightarrow\; x' = \frac{n\,x}{-z},\quad y' = \frac{n\,y}{-z} \]

손계산 · \( n=1 \), 점 \( (2,\,1,\,-4) \)
\( x' = 1\cdot 2 / 4 = 0.5 \), \( y' = 1\cdot 1/4 = 0.25 \)
같은 점을 8m 뒤로(\( z=-8 \)) → \( x'=0.25 \) · 두 배 멀면 절반 크기

창문 유리에 바깥 풍경 따라 그리기 · 눈을 한 자리에 고정하고 유리 위에 나무 윤곽을 그리면, 멀리 있는 나무일수록 유리 위 그림이 작아짐 · 유리 = near 평면, 그림 크기 = 실제 크기 ÷ 거리

원리 : 거리로 나눗셈 · 멀수록 \( -z \) 증가 → 나눈 결과 감소

문제 : 행렬 곱셈은 곱하고 더하기만 가능 → "z로 나누기"를 직접 표현할 방법 없음

- 창문 비유 : 뒤러(Dürer)의 원근 투시 장치와 같은 원리 · 유리창에 매직으로 따라 그리기 경험을 떠올리게 함 - 손계산을 칠판에 : 4m 거리 → 0.5, 8m 거리 → 0.25 - 마지막 줄의 문제를 다음 슬라이드가 해결
투영 · 3 ★

투영 행렬 — w 칸에 거리 저장

\[ P = \begin{bmatrix} \frac{1}{a\,t} & 0 & 0 & 0 \\[6pt] 0 & \frac{1}{t} & 0 & 0 \\[6pt] 0 & 0 & -\frac{f+n}{f-n} & -\frac{2fn}{f-n} \\[6pt] 0 & 0 & \color{#ff5a4d}{-1} & 0 \end{bmatrix} \]

\( t=\tan(\text{시야각}/2) \) · \( a \) = 종횡비 · \( n, f \) = near, far

동차좌표Homogeneous coords
(x, y, z) 뒤에 네 번째 칸 w 를 붙인 4칸 좌표 · 2주차에서는 점(w=1)과 방향(w=0) 구분용
원근 나눗셈Perspective divide
x, y, z 를 w 로 나누는 단계 · GPU가 자동 수행

마지막 행의 −1 → 곱셈 결과의 w 칸에 −z(=거리)가 담김 → 행렬로는 못 하는 나눗셈을 잠시 미뤄 두었다가 클리핑 이후 GPU가 w 로 나눔

- 붉은 −1 한 칸이 원근의 정체 : "곱셈 결과의 넷째 칸에 −z 를 복사해 두는 장치" - 행렬의 나머지 칸들은 상자 크기(시야각·종횡비)와 깊이 범위(near·far)를 맞추는 역할
투영 · 4

손계산 — 점 하나를 끝까지 따라가기

조건 : 시야각 90° (\( t=1 \)), 종횡비 1, \( n=1,\ f=100 \) · 뷰 공간의 점 \( (2,\,1,\,-4) \)

\[ \underbrace{(2,\ 1,\ -4,\ 1)}_{\text{뷰}} \xrightarrow{\;P\;} \underbrace{(2,\ 1,\ 2.06,\ \color{#ff5a4d}{4})}_{\text{클립}} \xrightarrow{\;\div w\;} \underbrace{(0.5,\ 0.25,\ 0.52)}_{\text{NDC}} \xrightarrow{\text{뷰포트}} \underbrace{(1440,\ 675)}_{1920\times1080} \]

투영 · 1 질문의 답
먼 물체가 작아지는 원인 = 투영 행렬 마지막 행의 −1
거리를 w 칸에 옮겨 두고 → GPU가 w 로 나눔
→ 멀수록 큰 수로 나뉘어 작아짐

w = 택배 상자에 붙인 "나중에 이 수로 나눌 것" 메모 · 행렬 공정에서는 나눌 수 없으니 나눌 값을 상자(w 칸)에 적어 보내고, 다음 공정(GPU)이 메모를 보고 나눔

- 앞 슬라이드 닮은꼴 손계산(0.5, 0.25)과 결과가 같다는 점 강조 → 행렬이 닮은꼴 계산을 대신하고 있음 - z 칸 2.06 : −(101/99)·(−4) − 200/99 ≈ 2.06 → ÷4 ≈ 0.52 (깊이 값, 깊이 블록에서 사용) - y 화면 좌표 675 : (0.25+1)·540 · 화면 위쪽이 0 인지 아래쪽이 0 인지는 API마다 다름 - 택배 메모 비유 : "계산을 못 끝냈으니 다음 사람에게 메모로 넘긴다"

깊이 값의 불균등 분포

거리 \( d \) 를 NDC 깊이(−1~+1)로 바꾸는 식

\[ z_{ndc} = \frac{f+n}{f-n} - \frac{2fn}{(f-n)\,d} \]

거리 \( d \) 가 분모에 있음 → \( 1/d \) 곡선 → near 근처는 숫자가 빠르게 변하고(촘촘), 멀어질수록 거의 안 변함(성김)

가까운 곳엔 촘촘하고 먼 곳엔 듬성듬성한 자 · 눈금 개수는 정해져 있는데 대부분이 자의 앞부분에 몰림 → 먼 곳에서는 2mm 차이를 잴 눈금이 없음

near=0.1, far=1000 이면 → 깊이 숫자의 절반이 0.1m~0.2m 구간에 배정 · 나머지 999.8m 가 남은 절반을 나눠 씀

- 자 눈금 비유 : 30cm 자인데 앞 1cm 에 눈금 절반, 나머지 29cm 에 나머지 절반 - 왜 이렇게 만드나? → 원근 나눗셈(÷w)을 깊이에도 똑같이 적용하기 때문 · 가까운 물체일수록 정밀한 것이 대체로 유리하다는 장점도 있음
깊이 · 3

숫자로 보는 깊이 눈금

near=0.1, far=1000 · 깊이 버퍼에 실제 저장되는 0~1 값 (\( z_{ndc} \) 를 0~1 로 옮긴 것)

\[ z_{buf} = \frac{f}{f-n}\left(1-\frac{n}{d}\right) \]
거리 d0.2 m1 m10 m100 m1000 m
저장 값0.5000.9000.9900.9991.000
쓰고 남은 몫절반 소진90% 소진99% 소진99.9% 소진—

10m~1000m 의 넓은 풍경 전체가 0.99~1.00 사이의 1% 안에서 앞뒤를 가려야 함 → 먼 곳의 바닥·그림자가 깜빡이는 직접적 이유

- 손계산 하나 : d=1 → (1000/999.9)·(1 − 0.1/1) ≈ 0.9 - "카메라 앞 1m 까지 이미 눈금의 90% 를 써 버렸다" 로 요약
깊이 · 4 ★

정밀도를 결정하는 값 : near

- 붉은 선(near 0.01/far 1000)과 노란 선(near 0.01/far 100)의 겹침 짚기 - 학생에게 먼저 질문 : "far 를 10분의 1로 줄였는데 왜 안 움직이죠?" - 답 : 1/near − 1/far 에서 1/1000, 1/100 모두 1/0.01 = 100 앞에서 무의미
깊이 · 5

깊이 분해능 공식

\[ \Delta d \approx \frac{d^2\left(\frac{1}{n}-\frac{1}{f}\right)}{2^{b}} \]

\( \Delta d \) = 거리 \( d \) 에서 구분 가능한 최소 간격 (깊이 분해능)
\( b \) = 깊이 버퍼 비트 수 · 보통 24 → \( 2^{24}\approx 1677\text{만} \)

near / far1/n − 1/f100m 에서 Δd
0.01 / 10000100.0약 60 mm깜빡임
0.01 / 10099.99약 60 mm동일하게 깜빡임
0.3 / 100003.33약 2 mm거의 정상

손계산 · near 0.01, 100m
\( 100^2 \times 100 \div 16{,}777{,}216 \approx 0.06\,\text{m} \) = 6cm
→ 6cm 보다 가까이 붙은 두 면은 같은 깊이로 기록

far 100배 감소 → 변화 없음 · near 30배 증가 → 정밀도 약 30배 향상 — 오늘 수업의 핵심 한 줄

- Δd 는 거리의 제곱에 비례 : 같은 설정이라도 10m 에서는 0.6mm, 100m 에서는 60mm - 이 공식은 24비트 정수 깊이 버퍼 기준의 근사식 · 다음 슬라이드에서 왜 near 가 지배하는지 정리

공식의 괄호 \( \tfrac{1}{n}-\tfrac{1}{f} \) 를 숫자로 비교

값1/값
near 0.010.01100

far 쪽의 1/f 는 어차피 0에 가까움 → far 를 아무리 바꿔도 괄호 값이 거의 그대로 · near 쪽의 1/n 이 괄호 값을 사실상 혼자 결정

정해진 눈금 1677만 개를 나눠 주는 예산 · 배분 규칙이 "카메라에 가까울수록 많이"라서, near 를 작게 잡을수록 카메라 코앞 몇 cm 에 눈금을 다 써 버림 · far 를 줄이는 것은 이미 거의 빈 지갑의 끝자리를 조정하는 셈

참고 : 최신 PC·콘솔은 깊이를 뒤집어 저장(reversed-Z)하고 32비트 실수를 써서 실제 수치가 훨씬 좋음 · 모바일·Quest는 기기·설정마다 다름 · near 우선 원칙은 동일

z-fighting 함정 재현

2mm 떨어진 두 면

청록 = 바닥면 · 분홍 = 그 위 2mm 에 붙인 스티커 · 왼쪽 아래 가까운 쌍은 간격이 같아도 정상

- 용어 : z-fighting = 깊이가 거의 같은 두 면이 깊이 버퍼에서 같은 숫자로 기록돼, 프레임마다 어느 쪽이 이길지 바뀌며 깜빡이는 현상 - 비유 : 1cm 눈금 자로 2mm 차이 나는 두 종이의 높이를 재면 둘 다 같은 눈금 → 매번 동전 던지기로 순서를 정하는 셈 - ① far 슬라이더만 10000 → 100 으로 끝까지 감소 · 깜빡임 변화 없음 → "far 를 줄이면 된다"는 통설 반박 - ② near 를 0.01 → 0.3 으로 증가 · 즉시 해결 - ③ 왼쪽 아래 가까운 쌍 : 같은 2mm인데 정상인 이유 → Δd 는 거리의 제곱에 비례

먼 바닥이 지직거린 이유와 해결

z-fightingZ-fighting · 깊이 다툼
거의 같은 깊이의 두 면(바닥과 그림자·스티커)이 깊이 버퍼에서 같은 숫자로 기록 → 프레임마다 이기는 쪽이 바뀌며 깜빡임

1cm 눈금 자로 2mm 차이 나는 두 종이 높이 재기 · 둘 다 같은 눈금 → 누가 위인지 매번 동전 던지기 · 카메라가 조금 움직일 때마다 결과가 바뀌어 무늬가 꿈틀거림

원인 : 코드가 아니라 Camera 의 near 값이 너무 작음 (예 : 0.01)
→ 깊이 눈금 대부분이 카메라 코앞에 몰림
→ 100m 지점에서는 약 6cm 보다 가까운 두 면을 구분 불가

해결 : near 를 카메라가 실제로 다가갈 최소 거리까지 키움 (예 : 0.3)
→ 100m 지점 구분 간격 약 2mm 로 개선
far 만 줄이는 것은 효과 거의 없음

- 도입 슬라이드의 질문을 다시 띄우고 한 문장으로 답 : "고칠 곳은 셰이더도 텍스처도 아닌 Camera 의 near 값" - 학생이 자기 말로 원인을 한 번 말해 보게 함

HMD 렌즈의 역할

HMD 화면 위치 : 눈에서 약 3~5cm 앞 → 사람 눈은 그렇게 가까운 곳에 초점을 맞출 수 없음

그래서 렌즈 사용 → 화면이 약 1.3~2m 앞에 있는 것처럼 보이게 함 (기기마다 다름) → 눈의 수정체가 편하게 풀린 상태로 볼 수 있는 거리

대가 : 이 렌즈가 상을 가장자리로 갈수록 더 크게 늘림 — 핀쿠션 왜곡 (실패가 바늘꽂이 쿠션처럼 모서리가 뻗은 모양)

해결 : GPU가 미리 반대 방향(배럴, 술통 모양)으로 오므려 렌더링 → 두 왜곡이 상쇄되어 반듯한 상

HMD 렌즈 = 돋보기 · 눈앞 글씨는 흐리지만 돋보기를 대면 크게, 편하게 보임 · 대신 돋보기 가장자리로 갈수록 글씨가 더 늘어나 휘어 보임

12주차 연결 : 렌즈가 만드는 "가상의 초점 거리" → 조절-수렴 충돌의 출발점

- 돋보기 비유 : 실제 돋보기를 신문 위에 대고 가장자리 글자가 늘어나는 모습을 보여 주면 효과적

왜 일부러 찌그러뜨려 그리는가

볼록 거울에 비칠 것을 알고 미리 반대로 찌그러뜨려 그린 그림 · 그림만 보면 이상하지만 거울에 비치면 반듯해짐 · 바닥에 길게 늘여 그려 한 지점에서 보면 입체로 보이는 거리 착시 그림과 같은 발상

비유의 한계 : 실제 렌즈는 거울과 달리 색마다 꺾는 정도도 달라 R·G·B 를 따로 보정

지각 · 1 질문의 답
렌즈 안쪽 화면이 일그러진 이유 = 고장이 아니라 렌즈 왜곡을 미리 상쇄하려고 GPU가 일부러 반대로 오므린 그림 · 렌즈를 통과해야 비로소 반듯해짐

- 볼록 거울 비유 : 아나모픽 아트(바닥에 늘여 그린 3D 착시 그림) 사진을 보여 주면 좋음 - "헤드셋 화면을 휴대폰으로 찍어 보면 이 오므린 그림이 그대로 보인다"

사전보정의 비용

렌더 해상도

배럴로 오므리면 중앙부 픽셀이 늘어남 → 중앙 화질을 지키려고 디스플레이보다 약 1.2~1.4배 크게 렌더링 (기기마다 다름)

색수차 보정

렌즈가 색마다 다르게 꺾음 → R·G·B 를 서로 다른 배율로 왜곡 · 사실상 그림을 세 번 읽음

후처리 한 패스

왜곡은 렌더링이 끝난 뒤 화면 전체에 한 번 더 적용 · 11.1ms 예산에서 먼저 빠지는 몫

색수차 = 프리즘 무지개 · 유리가 색마다 빛을 다르게 꺾어 흰빛이 무지개로 갈라지듯, 렌즈 가장자리에서 흰 글자 테두리가 빨강·파랑으로 번짐

이 보정은 합성기(compositor) — 헤드셋 운영체제가 완성된 두 장을 받아 왜곡 보정 · 마지막 순간 머리 움직임에 맞춘 그림 이동(timewarp)을 하는 프로그램 — 가 담당 · 개발자 몫은 11.1ms 중 그 나머지

아이박스 — 눈동자 허용 범위

아이박스(eyebox) : 렌즈가 정상적인 상을 만드는 눈동자 위치 범위 · 한 변 약 10mm 안팎 (기기마다 다름)

범위를 벗어나면 → 화면 가장자리 어두워짐(비네팅), 색 번짐, 초점 흐려짐

쌍안경 접안렌즈 · 눈을 정확한 자리에 대야 둥근 시야가 꽉 차고, 조금만 비켜도 가장자리가 까맣게 가려짐

"화질이 나쁘다"는 불만의 상당수 = 헤드셋 착용 불량 (위치·각도·IPD 조절 미흡)

14주차 플레이테스트 : 착용 상태 우선 확인 · 아이박스를 벗어난 사람의 화질 평가 → 콘텐츠 평가로 활용 불가

- 쌍안경 비유 : 실제로 쌍안경을 돌려 보며 눈 위치를 비키게 해 보면 즉시 이해 - 원래 슬라이드의 "절반"은 근거 수치가 아니므로 "상당수"로 표현

IPD — 사람마다 다른 상수

IPD(동공간 거리) : 두 눈동자 중심 사이의 거리 · 성인 대부분 약 53~73mm, 평균 약 63mm → 평균값 하나로 모든 사용자 대응 불가

IPD 가 안 맞으면 → 두 눈의 상이 어긋남 → 뇌가 하나로 합치려고(융합) 계속 애씀 → 눈 피로

두 눈 사이가 아주 넓은 거인의 시점 · 가상 카메라 간격을 넓히면 사용자는 거인이 된 것처럼 느낌 → 세상이 장난감처럼 작아 보임

IPD 적용 위치 두 곳 : 렌즈 간격(하드웨어)과 가상 카메라 간격(소프트웨어)
둘이 다르면 세상의 크기 감각 왜곡

카메라 간격 임의 확대 → 세상이 장난감처럼 작게 보임 · 축소 → 세상이 거대하게 보임

- 거인 비유 : 실제 "미니어처 사진(틸트 시프트)" 처럼 보이는 현상 · 반대로 간격을 줄이면 개미가 된 느낌

비대칭 절두체를 쉽게

일반 카메라 상자 : 정면 기준 좌우 대칭 → 시야각 하나(fieldOfView)로 표현 가능

VR 각 눈의 상자 : 코 쪽은 좁고, 귀 쪽은 넓음 (사람 눈의 시야도 코 쪽이 좁음) → 두 눈을 합친 전체 시야는 넓히고, 가운데 겹치는 구간에서 입체감 확보 → 좌우 각도가 서로 다름

fieldOfView 는 숫자 하나 → "왼쪽 40°, 오른쪽 50°" 같은 모양 표현 불가

창문 하나를 두 사람이 나란히 서서 보기 · 창문 왼쪽 앞에 선 사람은 창이 오른쪽으로 치우쳐 보이고, 오른쪽 사람은 반대 · 각자 보는 시야가 정면 기준으로 한쪽에 쏠림 → 비대칭 상자

비유의 한계 : 헤드셋은 눈마다 화면이 따로 있지만, 렌즈·화면 중심이 눈동자 정면에서 비켜 있어 같은 쏠림 발생

이 모양은 렌즈·화면 배치를 아는 헤드셋(XR 런타임)만 정확히 계산 가능

// 문법 정상
// 에디터에서 정상 동작
// 요구 사항 모두 포함

// far / near = 1,000,000 : 1

학생이 해야 할 지적

"far 가 아니라 near 가 문제다."

정밀도를 결정하는 값 : 1/near − 1/far
far=10000 → 1/far = 0.0001 ≈ 0
near=0.01 → 1/near = 100

// near 0.01 → 0.3
// 정밀도 약 30배, 먼 시야는 그대로

// far/near 상한을 명세에 명시

위험한 이유 : 개발자 화면에서는 정상으로 보임 · 카메라가 멀리 있고 움직일 때만 드러남

- 학생들이 이 프롬프트를 그대로 입력하도록 진행 - 모델의 응답을 각자 확인하고 near 값을 소리내어 읽기 - 결과는 0.01 ~ 0.03 처럼 Unity 기본값(0.3)보다 훨씬 작은 값이 자주 나옴
함정 · 2

AI가 이 값을 반복하는 이유

  • Unity 기본값은 near 0.3 · far 1000 → 그런데 "가까이 가면 물체가 잘려요" 해결 글에서 near 를 0.01 수준으로 낮추라는 답이 흔함
  • near 를 작게 잡으면 물체가 카메라를 뚫는 문제 방지 — 즉시 보이는 안전
  • far 를 크게 잡으면 먼 물체 사라짐 방지 — 역시 즉시 보이는 안전
  • z-fighting 은 멀리서, 움직일 때만 드러나는 증상 → 정지 화면·짧은 테스트에서 잘 안 보임

이번 주 명세 예시

[목표]
지형 위를 따라다니는 3인칭 카메라. 시야 거리 500m.

[제약]
- 깊이 버퍼는 24비트를 쓴다
- nearClipPlane 은 0.1 이상일 것
- farClipPlane / nearClipPlane 비율이 5,000 을 넘지 않을 것
- 카메라 파라미터는 인스펙터에서 조정 가능할 것

[검증 조건]
- 200m 지점의 바닥 위에 두께 0 인 데칼을 올려 두고
  카메라를 좌우로 5초간 흔들었을 때 깜빡이는 픽셀이 0 일 것
- 위 공식 Δd = d²(1/n - 1/f) / 2^24 로 계산한
  200m 에서의 Δd 가 5mm 이하일 것

[비목표]
- 충돌 처리, 카메라 흔들림 연출, 후처리는 만들지 말 것

손계산 · near 0.1, far 500, 200m
\( 200^2\times 9.998 \div 2^{24} \approx 0.024\,\text{m} \) = 24mm → 불합격
5mm 이하가 되려면 near ≥ 약 0.48
→ 제약(0.1 이상)만 지켜서는 부족 · 검증 조건이 near 를 더 끌어올림

두 검증 조건의 유형 차이 : 하나는 관찰로 측정, 하나는 계산으로 측정
