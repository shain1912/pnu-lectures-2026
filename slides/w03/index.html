씬 = 무대 하나

Unity 프로젝트 = 여러 개의 씬(Scene, 한 장면 파일)으로 구성
예 : 타이틀 화면, 1스테이지, 엔딩이 각각 하나의 씬

씬 안의 물체 목록 → Hierarchy 창(계층 창)
선택한 물체의 부품과 설정값 → Inspector 창(속성 창)

씬 = 연극의 한 막 무대 — 무대 위에 배우·소품·조명이 놓이듯 씬 위에 게임오브젝트가 놓임

Hierarchy = 출연진 명단, Inspector = 명단에서 고른 배우 한 명의 프로필 카드

- Unity 에디터 화면을 띄워 Hierarchy 와 Inspector 위치를 손으로 가리키며 설명 - "무대가 바뀌면 출연진도 바뀌죠. 씬을 바꾸면 Hierarchy 목록도 통째로 바뀝니다"

게임오브젝트 = 빈 레고 판

GameObject : 이름과 트랜스폼(위치·회전·크기)만 가진 빈 틀
그 자체로는 보이지도, 움직이지도 않음

화면에 보이게 하려면 → MeshRenderer(그리기 부품) 추가
중력으로 떨어지게 하려면 → Rigidbody(물리 부품) 추가

Unity에서의 제작 = 빈 판에 필요한 부품을 골라 끼우는 과정
기능은 판이 아니라 부품에서 나옴

게임오브젝트 = 빈 레고 판, 컴포넌트 = 판에 끼우는 레고 부품 — 바퀴를 끼우면 굴러가고 램프를 끼우면 빛남. 같은 판도 끼운 부품에 따라 자동차도, 집도 됨

디자인 툴로 치면 빈 레이어에 효과(그림자·테두리)를 얹는 방식과 같은 발상

- 에디터에서 Create Empty 로 빈 게임오브젝트 생성 → 아무것도 안 보임을 확인 - MeshRenderer 를 붙여 보이게, Rigidbody 를 붙여 떨어지게 — 부품 하나씩 끼우며 시연 - "레고 판만 있으면 아무것도 못 하죠. 바퀴를 끼워야 굴러갑니다"

상속과 조합 — 기능을 늘리는 두 가지 방법

클래스Class
물체의 설계도 · 어떤 데이터와 동작을 가지는지 정의
상속Inheritance
기존 설계도를 물려받아 기능을 덧붙인 새 설계도 작성 (FlyingEnemy ← Enemy)
조합Composition
설계도를 늘리지 않고 부품을 골라 붙여 기능 구성

이동 방식 3가지(걷기·날기·헤엄) × 공격 방식 4가지 → 상속으로는 설계도 최대 12개, 조합으로는 부품 7개(3 + 4)로 해결

상속 = 완제품 장난감 라인업 — «날면서 폭탄 쏘는 로봇» 이 필요하면 신상품을 따로 출시해야 함
조합 = 레고 — 날개 부품과 폭탄 부품을 꺼내 끼우면 끝

- 조합의 수가 곱셈으로 늘어나는 «조합 폭발» 을 숫자로 먼저 보여준 뒤 다음 장 도해로 - "새 적이 필요할 때마다 장난감 공장에 신상품 주문을 넣는 방식 vs 레고 상자에서 부품 꺼내는 방식"

내 코드도 부품 — C# 스크립트

using UnityEngine;

public class Spinner : MonoBehaviour   // ← 이 상속 = "부품 자격증"
{
    public float speed = 45f;          // ← Inspector 에 입력칸으로 노출

    void Start()   { }   // 씬에 등장한 뒤 첫 프레임 직전에 한 번
    void Update()  { }   // 매 프레임 한 번
}

MonoBehaviour 상속 → 게임오브젝트에 붙일 수 있는 부품이 됨
public 변수 → Inspector 에 입력칸으로 노출 → 코드 수정 없이 값 조절 가능
Start · Update 를 부르는 주체 = Unity — 내 코드에서 직접 호출하지 않음

- 스크립트 파일을 게임오브젝트로 끌어다 놓는 순간 Inspector 에 Spinner 부품과 speed 입력칸이 생기는 장면 시연 - 디자이너가 코드를 열지 않고 숫자만 바꿔 조정할 수 있다는 점이 public 변수의 장점

Unity 가 내 코드를 부르는 방식

MonoBehaviourMonoBehaviour
Unity 가 제공하는 «부품 자격» 클래스 · 이를 상속해야 게임오브젝트에 붙일 수 있음
이벤트 함수Event Function
정해진 이름으로 만들어 두면 Unity 가 알맞은 때에 자동 호출하는 함수 (Awake, Start, Update …)
StartStart()
오브젝트가 활성화된 뒤 첫 Update 직전에 1회
UpdateUpdate()
매 프레임 1회

연극 배우와 무대감독 — 배우(내 스크립트)는 스스로 무대에 나가지 않고 무대감독(Unity)의 큐 신호에 맞춰 연기. Start = 첫 등장 큐, Update = 매 장면 반복되는 큐

큐 이름이 틀리면(update 처럼 소문자) 신호가 오지 않아 오류 없이 아무 일도 안 일어남

- "여러분이 Update 를 부르는 게 아니라, Unity 가 큐 사인을 줄 때 여러분 코드가 무대에 나가는 겁니다" - 대소문자 오타가 오류 메시지 없이 조용히 실패하는 대표 사례 — 초보자가 가장 많이 헤매는 지점

게임 = 멈추지 않는 반복(루프)

while (게임 실행 중) { 입력 읽기 세상 상태 갱신 한 장 그리기 }

루프 한 바퀴 = 그림 한 장 = 한 프레임
1초에 도는 바퀴 수 = fps(초당 프레임 수)
PC·장면마다 다름 · 보통 30~144, 흔한 기준 60

Update() = 루프 한 바퀴마다 끼워 넣는 내 코드
Update 안이 무거움 → 한 바퀴가 길어짐 → fps 하락 → 게임 전체가 버벅임

게임 루프 = 플립북 — 한 장씩 그려 빠르게 넘기면 움직임으로 보임 · 1초에 넘기는 장 수 = fps

- 노트 모서리에 그린 플립북을 떠올리게 하기 : "그림 한 장 = 프레임, 넘기는 속도 = fps" - 플립북과 다른 점 : 게임은 미리 그려 둔 그림이 아니라 매 장을 그 자리에서 새로 그림 — 그래서 한 장에 걸리는 시간이 매번 다름 (뒤의 deltaTime 으로 연결)

fps 와 한 프레임의 시간

\[ \text{한 프레임 시간} = \frac{1000\ \text{ms}}{\text{fps}} \]
fps306090120
한 프레임 시간33.3ms16.7ms11.1ms8.3ms
흔한 예저사양 노트북일반 모니터VR 헤드셋고주사율 모니터

ms(밀리초) = 1/1000초 · fps 가 높을수록 → 한 장에 쓸 수 있는 시간이 짧아짐
화면은 정해진 주기로 새 그림으로 교체 · 그 주기에 맞춰 그림을 내보내는 장치 = vsync(수직 동기화)

- 계산 연습 : "60fps 면 한 장에 몇 ms?" → 1000 ÷ 60 ≈ 16.7 - 90fps 의 11.1ms 는 Part II VR 에서 다시 등장 — 미리 표시 - vsync 는 다음 장 도해 오른쪽 끝 «vsync 대기» 칸의 의미

한 프레임의 실행 순서

- 순서 : 입력 수집 → FixedUpdate(0~여러 번) → Update → LateUpdate → 렌더링 → vsync 대기 - 시작할 때 한 번 : Awake → OnEnable → Start, 그 뒤 매 프레임 위 순서 반복 - 플립북 한 장을 그리는 작업 순서표라고 소개

함수별 역할

함수호출 시점용도
Awake오브젝트가 만들어질 때 1회 (Start 보다 먼저)자기 자신 초기화, 부품 미리 찾아 두기(캐싱)
Start첫 Update 직전 1회다른 오브젝트를 참조하는 초기화 — 이 시점엔 다른 오브젝트들의 Awake 완료
FixedUpdate게임 시간 0.02초마다(기본값, 설정에서 변경 가능) · 한 프레임에 0~여러 번Rigidbody 에 힘을 주는 코드
Update매 프레임 1회입력 처리, 게임 규칙, 타이머
LateUpdate그 프레임의 모든 Update 가 끝난 뒤 1회카메라 추적, 다른 대상을 따라가는 코드

캐싱(caching) = 한 번 찾은 것을 변수에 저장해 두고 재사용
같은 코드라도 어느 함수에 넣느냐에 따라 결과가 달라짐 → 다음 장 예시

카메라 추적은 왜 LateUpdate 인가

여러 스크립트의 Update 실행 순서 = 정해져 있지 않음
카메라의 Update 가 플레이어의 Update 보다 먼저 실행 → 카메라는 플레이어의 이동 전 위치를 따라감
→ 다음 프레임에 뒤늦게 따라잡음 → 화면이 미세하게 떨림(jitter)

LateUpdate = 모든 Update 가 끝난 뒤 실행
→ 플레이어가 이번 프레임 이동을 마친 위치를 확실히 따라감 → 떨림 해결

단체 사진 촬영 — 사람들이 아직 자리를 옮기는 중에 셔터를 누르면 흔들린 사진. 모두 자리를 잡은 뒤(LateUpdate) 셔터를 눌러야 선명

- "카메라 = 사진사, 플레이어 = 모델. 모델이 움직이는 중에 찍으면 안 되죠" - Part III 실습 5번(확장)에서 Update / LateUpdate 양쪽에 넣어 떨림을 직접 재현

- x = 플레이어 위치(칸) · 오차 = 카메라가 따라간 위치와 실제 플레이어 위치의 차이 - 위 줄 : 프레임 N 에서는 카메라가 먼저 실행되어 이동 전 위치(0)를 봄 → 화면에선 1칸 뒤처짐, N+1 에서는 순서가 바뀌어 맞음 → 오차가 들쭉날쭉 = 떨림 - 아래 줄 : LateUpdate 는 항상 모든 Update 뒤 → 오차 0

Time.deltaTime — 프레임 대신 시간으로 계산

deltaTime = 직전 프레임 하나가 걸린 시간(초) · 30fps 면 약 0.033초, 120fps 면 약 0.0083초
이동량 = 속도 × deltaTime → 느린 PC 는 한 번에 많이, 빠른 PC 는 한 번에 조금 이동

speed = 5cm (초당)한 프레임 이동량1초 이동 거리
노트북 30fps5 × 0.033 ≈ 0.167cm0.167 × 30 ≈ 5cm
데스크톱 120fps5 × 0.0083 ≈ 0.042cm0.042 × 120 ≈ 5cm

걸음 수가 아닌 시간 기준 이동 — «100걸음 걸어라» 는 보폭에 따라 도착 거리가 다름. «1초에 5cm 속도로 걸어라» 는 큰 걸음을 드문드문 걷는 사람(느린 PC)이든 종종걸음을 자주 걷는 사람(빠른 PC)이든 같은 시간에 같은 거리

- deltaTime 을 곱하는 순간 speed 의 단위가 «프레임당» 에서 «초당» 으로 바뀜 - 비유 정리 : 느린 PC = 큰 걸음 드문드문, 빠른 PC = 작은 걸음 자주 — 1초 뒤 도착 지점은 같음
시간 · 2 도해

30fps vs 120fps — 1초 동안 간 거리

- 왼쪽 = 시간 · 1 표 (5 × 30 = 150, 5 × 120 = 600) · 오른쪽 = 시간 · 2 표 (둘 다 약 5) - 눈금이 100배 다르다는 점을 먼저 짚기 — 오른쪽 막대가 길다고 더 멀리 간 것이 아님

AI 함정 #2

AI가 빠뜨리는 단어 하나

AI가 자주 작성하는 코드

void Update() {
  transform.Translate(
    Vector3.forward * speed);
}

// 프레임마다 speed 만큼
// = PC 성능이 곧 속도

필요한 코드

void Update() {
  transform.Translate(
    Vector3.forward * speed
    * Time.deltaTime);
}

// 초당 speed 만큼

이 함정은 화면에서 잘 드러나지 않음 — 개발자 PC 에서는 정상처럼 보임
프레임률을 바꿔 측정해야 확인 가능 → Part III 실습의 검증 방법

- transform.Translate = 트랜스폼 부품의 위치를 주어진 만큼 옮기는 함수 - AI 가 짧은 예제 코드를 만들 때 deltaTime 을 생략하는 경우가 잦음 — 실습 1번에서 직접 확인
도입 질문의 답

같은 코드인데 왜 속도가 달랐나

  1. 이동 코드가 «매 프레임 speed 만큼» 이동 — Time.deltaTime 누락
  2. 노트북 30fps, 데스크톱 120fps → 1초 동안 Update 호출 횟수 30번 vs 120번
  3. 이동 거리 = speed × 호출 횟수 → 데스크톱 캐릭터가 4배 멀리 이동

해결 : speed * Time.deltaTime → «프레임당» 이 아닌 «초당» 이동
→ 어느 PC 에서든 같은 시간에 같은 거리

이런 결함의 이름 = 프레임률 종속(frame-rate dependent) · 화면만 봐서는 발견하기 어려움

- 수업 첫 질문으로 돌아가 답을 명확히 닫기 - "노트북이 느렸던 게 아니라, 코드가 PC 성능을 속도로 바꿔 버린 것"

끊김 : 게임은 짜증, VR은 멀미 — 왜?

  1. 모니터 게임 : 화면은 내 몸과 따로 있는 창문 → 끊겨도 눈만 불편, 몸의 균형 감각과는 무관
  2. VR : 화면이 곧 내 시야 전체 → 고개를 돌릴 때 전정계는 «돌았다», 눈은 «아직 안 돌았다»
  3. 두 감각의 어긋남 = 2주차 감각 충돌 → 메스꺼움 · 어지럼

결론 : VR 에서 프레임 시간 = 화질 문제가 아닌 몸의 편안함 문제
→ 프레임 예산 지키기 = VR 설계 원칙 1번

실습 · 2

보이지 않는 결함의 측정

// 프레임률을 강제로 낮춰서 같은 코드를 두 번 실행
void Awake() {
    QualitySettings.vSyncCount = 0;          // vsync 끄기 — 꺼야 아래 설정이 적용
    Application.targetFrameRate = 30;        // 그 다음 120 으로 바꿔 한 번 더
}

// 10초 뒤 위치를 콘솔에 출력해 비교
void Start() { Invoke(nameof(Report), 10f); }
void Report() { Debug.Log($"{Application.targetFrameRate}fps → {transform.position}"); }

30fps 와 120fps 에서 10초 뒤 위치 비교 → 같으면 통과, 다르면 deltaTime 누락 → 이것이 검증 조건
vSyncCount 를 0 으로 두지 않으면 targetFrameRate(목표 프레임률) 무시 (PC 기준) — 자주 하는 실수

- Invoke = 정해진 시간 뒤에 함수 실행, Debug.Log = Unity 콘솔 창에 글자 출력 - VR 기기·모바일에서는 targetFrameRate 동작이 다를 수 있으므로 에디터(PC)에서 측정

#실습확인할 개념
1 AI에게 검증 조건 없이 회전·이동 스크립트 요청 · 첫 응답의 deltaTime 포함 여부 확인 명세의 빈틈
2 위 측정 코드로 30fps / 120fps 비교, 결함 확인 보이지 않는 결함의 측정
3 검증 조건을 넣어 다시 요청, 응답 차이 비교 명세에 따른 결과 변화
4 공을 Update 와 FixedUpdate 에서 각각 밀어 차이 비교 고정 타임스텝
5 카메라 추적을 Update 와 LateUpdate 양쪽에 넣어 떨림 재현 (확장) 실행 순서

1~4 필수, 5 확장 · 제출물 없음, 수업 안에서 완료
