## 1. 이 평가가 확인하는 것

> «AI 가 이 코드를 짰다. **왜 이렇게 짜야 했는지** 설명하라.»

- 이 수업의 명제 : AI 시대에 그래픽스 이론을 배우는 이유 = **AI 에게 무엇을 요구할지 알고, AI 결과가 왜 틀렸는지 판별하기 위해서**
- 그래서 보는 것 3가지
  1. **결과물** — 씬이 개념을 «보여 주는» 실험대로 동작하는가
  2. **구술 방어** — 코드·설정의 이유를 개념 단어로 설명할 수 있는가
  3. **프롬프트 로그** — 명세가 개념을 정확한 용어로 담았는가 · 틀린 결과를 어떻게 잡아냈는가
- 코드를 직접 쳤는지는 평가 대상이 아님 · **AI 사용은 허용 · 권장** (단, 로그 전문 제출 의무)

## 2. 무엇을 만드나 — 지각 실험실 씬의 완성판

2주차부터 매주 누적해 온 **본인의 지각 실험실(Perception Lab) 씬**을 정리한 것.
새 작품을 처음부터 만들 필요 없음 · 예쁜 작품이 아니라 **개념을 검증하는 실험대**.

### 필수 요건

| # | 요건 | 확인 방법 |
|---|---|---|
| 1 | **인터랙션** 1개 이상 — 키보드·마우스 입력으로 무언가를 조작 | 시연 |
| 2 | **개념 장치 3개 이상** — 서로 다른 주차(2~7주)의 개념을 켜고 끄며 보여 주는 스위치 | 시연 + 검증 리포트 |
| 3 | **7주 이동 2종** — Transform 직접 이동(함정) ↔ Rigidbody 이동(정답) 전환 | 시연 |
| 4 | **측정값** — 개념 장치마다 수치 1개 이상 (ms · 횟수 · m · fps · 패턴 등) | 검증 리포트 |
| 5 | **AI 함정 1개 이상 재현 → 수정** — 같은 씬 안에서 전후 비교 | 시연 + 로그 |

### 개념 장치 예시 (고르거나 변형)

| 주차 | 장치 예 | 측정값 예 |
|---|---|---|
| 2 | 오일러각 회전 ↔ 쿼터니언 회전 토글 · 짐벌락 재현 | 잠기는 각도 (°) |
| 3 | deltaTime 있음/없음 이동 · fps 제한 30/60/144 | 같은 시간 이동 거리 (m) |
| 4 | near 0.01 ↔ 0.3 토글 · 먼 겹친 면 | z-fighting 발생 거리 (m) |
| 5 | 그림자 광원 수 · 베이크 전후 · 접촉 그림자 on/off | 프레임타임 (ms) |
| 6 | 밉맵 on/off · Alpha Blend ↔ Alpha Clip | 반짝임이 시작되는 거리 (m) |
| 7 | Transform ↔ Rigidbody 이동 · CCD on/off · Interpolate | 벽 통과 횟수 / 20 · 흔들림 폭 (m) |

### 프롬프트 로그 작성 규칙

- **전문** : 첫 요청부터 마지막까지 · 중간에 버린 대화도 포함
- 대화마다 맨 위에 **도구 이름 · 날짜** 한 줄 (예 : `Claude · 2026-10-18`)
- 개인정보(이메일·API 키 등)는 가림 표시 `[가림]` 허용 · 그 외 편집 금지
- 여러 도구를 썼으면 도구별로 나눠 묶기
- 로그 맨 앞에 **«핵심 전환점 3곳»** 목록 (예 : 「12번째 요청에서 velocity 를 linearVelocity 로 고치라고 지적」) — 채점자가 찾아볼 위치

> 왜 전문인가 : 좋은 결과보다 **틀린 결과를 어떻게 알아챘는지**가 개념 이해의 증거 · 실패 기록이 오히려 점수가 되는 항목

### 검증 리포트 양식 (개념 장치 1개당 반 쪽~1쪽)

```
## 장치 N : (이름) — (주차) 주차 개념 : (개념 이름)

1. 개념 한 줄 : (예) 이산 판정은 도착 자리만 검사 → 한 스텝 이동이 벽+크기보다 크면 통과 가능
2. AI 에게 준 명세 (4칸 중 검증 조건만 인용해도 됨)
3. 측정 조건 : 속도 · 설정값 · 반복 횟수 · 기기(PC/모니터 Hz)
4. 측정값 : 표 또는 로그 캡처
   | 조건 | 결과 |
   | Transform 이동 · 40 m/s | 20회 중 통과 17회 |
   | Rigidbody + Continuous Dynamic · 40 m/s | 20회 중 통과 0회 |
5. 판정 : 검증 조건 통과 / 실패 · 실패면 원인과 재요청 내용
6. AI 가 틀렸던 점 (있으면) : 무엇이 틀렸고, 어떤 개념으로 알아챘는가
```

### 동료 크리틱 양식 (현장 양식 B 와 같은 구조)

- 크리틱의 대상 = **씬과 프롬프트** · 사람이 아님
- 모든 칸을 **관찰 → 근거 → 제안** 으로 · «멋있음 / 별로» 같은 평가어 단독 사용 금지

| 칸 | 쓰는 것 | 예 |
|---|---|---|
| 관찰 | 본 것 그대로 · 조건 + 현상 | 대시하면 공이 얇은 벽을 가끔 통과 |
| 근거 | 수업 개념과 연결 (몇 주차 무엇) | 빠른 물체 + 이산 충돌 판정 (7주 · 함정 #6) |
| 제안 | 확인 방법 또는 명세에 넣을 문장 | Collision Detection 을 Continuous Dynamic 으로 바꿔 20회 발사 비교 |

```
작성자 : (본인)   대상 : (내 다음 발표 순서 동료)

크리틱 1 — 개선 제안 : 관찰 / 근거 / 제안
크리틱 2 — 잘된 점   : 관찰 / 근거 / 제안 (11주 VR 포팅 때 유지·확장할 점)
질문 하나 : «○○ 를 껐을 때 무엇이 바뀌나요?» 처럼 켜고 끄거나 숫자로 확인 가능한 질문
```

## 8. 자주 묻는 질문

- **AI 가 다 짜 줬는데 괜찮나요?** → 괜찮음 · 대신 구술에서 «왜» 를 설명해야 하고, 로그에서 본인이 무엇을 요구·지적했는지 보여야 함
- **씬이 예쁘지 않아도 되나요?** → 됨 · 평가 대상은 개념 장치와 측정값 · 미적 완성도는 기말 팀 프로젝트에서
- **Mac 에서 작업했는데 Windows 빌드가 없어요** → 프로젝트 zip (Library 제외) + 시연 영상으로 제출 · 당일 실습실 PC 에서 열어 시연
- **로그가 너무 길어요** → 길이 제한 없음 · 맨 앞 «핵심 전환점 3곳» 만 꼭 작성
- **질문 은행에 없는 질문도 나오나요?** → 원칙적으로 은행 안에서 · 단, 로그·리포트 내용에 대한 확인 질문은 추가될 수 있음
