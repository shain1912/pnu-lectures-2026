## 0. 읽는 법

### 0-1. AI 함정이란

- AI 가 **문법 오류 없이, 그럴듯하게, 그러나 틀리게** 짜는 그래픽스 코드·설정
- 대부분 에디터 화면에서는 «정상처럼» 보임 → 개념을 아는 사람이 **조건을 바꿔 측정**해야만 드러남
- 이 수업에서는 매주 하나씩 일부러 만나 보고 → 증상을 재현하고 → 원인을 개념으로 설명하고 → 고치는 문장을 명세에 넣는 연습

### 0-2. 항목 구성

| 칸 | 뜻 |
|---|---|
| 증상 | 화면·성능·몸에서 무엇이 어떻게 이상한가 |
| 재현 프롬프트 예 | 이 함정이 잘 나오는 요청 문장 — 실습에서 일부러 입력해 보는 용도 |
| AI 가 흔히 내놓는 것 | 대표 코드·설정 |
| 원인 (개념) | 그 결과가 틀린 이유를 수업 개념으로 |
| 진단 도구 | 무엇으로 확인하나 · 판정 기준 |
| 수정 프롬프트 | 명세 4칸(목표·제약·검증 조건·비목표)에 넣을 문장 |

### 0-3. 용어 풀이

| 용어 | 쉬운 뜻 |

| 프롬프트 (Prompt) | AI 에게 보내는 요청 문장 |

## #1 오일러각 회전 → 짐벌락 (2주)

- **증상**
  - 회전이 특정 각도(피치 X 가 ±90° 근처)에서 한 방향으로 잠김 · 좌우 회전(요)과 기울이기(롤)가 같은 움직임
  - 인스펙터 Rotation 값이 갑자기 튐 (예 : 90 → 270 으로 표시 변경)
- **재현 프롬프트 예** : «큐브가 부드럽게 회전하게 스크립트를 만들어줘»
- **AI 가 흔히 내놓는 것**

  ```csharp
  transform.eulerAngles += new Vector3(0, spd * dt, 0);
  ```

  - eulerAngles 누적 · 매 프레임 쿼터니언 → 오일러 변환 · 회전 중심 미지정
- **원인 (개념)**
  - 오일러각 = 세 축 각도를 **차례로** 돌린 결과 (Unity 인스펙터 순서 : 월드 축 기준 Z → X → Y)
  - 회전 합성은 **교환법칙 불성립**(비가환) → 순서·축 기준이 바뀌면 다른 자세
  - 가운데 축(X)이 90° 가 되면 바깥 축(Y)과 안쪽 축(Z)이 같은 축으로 정렬 → **자유도 3 → 2** = 짐벌락 · 오일러 표현 자체의 구조적 한계
- **진단 도구**
  - 2주 데모 «피치 90° 조작» · 인스펙터에서 X = 90 으로 두고 Y · Z 를 각각 조작 → 같은 움직임이면 짐벌락
  - 회전 값 로그 : 피치 85~95° 구간에서 프레임 간 각도 변화량 기록
- **수정 프롬프트**

  ```
  [목표] 큐브를 월드 Y축 기준으로 초당 45° 등속 회전시킨다.
  [제약] 회전 누적에 eulerAngles 를 쓰지 말 것 (짐벌락·값 튐)
         Quaternion 을 유지한 채 누적할 것 · Time.deltaTime 사용 · 회전 중심은 물체 원점
  [검증 조건] 60fps 와 30fps 에서 10초 뒤 각도가 같을 것 · 어떤 각도에서도 축이 잠기지 않을 것
  [비목표] 입력 처리, UI
  ```

- **재발 방지 규칙** : `회전 누적에 eulerAngles 금지 → Quaternion 곱 (transform.rotation *= Quaternion.Euler(...)) 또는 Rotate · 이유 : 짐벌락 (#1)`

## #2 deltaTime 누락 · Update 안 GetComponent 반복 (3주)

- **증상**
  - 같은 코드인데 PC 마다 이동 속도가 다름 — 30fps 노트북보다 120fps 데스크톱이 **4배 멀리** 이동
  - 오브젝트가 많아지면 프레임 저하 (Update 안에서 매번 부품·오브젝트 검색)
  - 개발자 PC 에서는 정상처럼 보임 → **프레임률을 바꿔 측정해야** 발견
- **재현 프롬프트 예** : «WASD 로 캐릭터가 앞으로 걸어가게 해줘» · «플레이어에 힘을 주는 스크립트 만들어줘»
- **AI 가 흔히 내놓는 것**

  ```csharp
  void Update() {
      transform.Translate(Vector3.forward * speed);          // 프레임마다 speed 만큼
      GetComponent<Rigidbody>().AddForce(Vector3.up);         // 매 프레임 부품 검색
      GameObject.Find("Player").transform.position = p;       // 매 프레임 씬 전체 검색
  }
  ```

- **원인 (개념)**
  - 게임 루프 : Update 는 **프레임마다** 1번 → 1초 호출 횟수 = fps → 이동 거리 = speed × fps = 프레임률 종속
  - `Time.deltaTime` = 지난 프레임이 걸린 시간 → 곱하면 «프레임당» 이 «초당» 으로 바뀜 = 프레임 독립성
  - `Find` 는 씬 전체를 이름으로 뒤짐 → 오브젝트 1,000개면 최악 매 프레임 1,000번 비교
- **진단 도구**
  - `Application.targetFrameRate` 로 30 · 120fps 고정 → 10초 이동 거리 비교
  - Unity Profiler (성능 측정 도구) 에서 Update 시간 확인
- **수정 프롬프트**
  - 제약 : «이동·회전은 초당 값 × Time.deltaTime» · «GetComponent · Find 는 Awake 에서 한 번만 하고 변수에 저장(캐싱)»
  - 검증 조건 : «30fps 와 120fps 에서 10초 이동 거리 차 1% 이하»
  - 손계산 : deltaTime 누락 · 프레임당 0.05 m → 30fps 10초 15 m · 120fps 60 m → 차 300% → 불합격
- **재발 방지 규칙**
  - `이동·회전은 초당 값 × Time.deltaTime · 이유 : 프레임 독립성 (#2)`
  - `GetComponent/Find 는 Awake 에서 한 번 · Update 안 검색 금지 (#2)`

## #3 near/far 오설정 → z-fighting (4주)

- **증상**
  - 먼 곳의 겹친 면(바닥 위 데칼·도로 표시)이 줄무늬로 깜빡임 · 카메라가 **멀리 있고 움직일 때만** 두드러짐
  - 정지 화면·짧은 테스트에서는 잘 안 보임
- **재현 프롬프트 예** : «멀리까지 잘 보이는 3인칭 카메라 만들어줘»
- **AI 가 흔히 내놓는 것**

  ```csharp
  cam.nearClipPlane = 0.01f;
  cam.farClipPlane  = 10000f;   // far / near = 1,000,000 : 1
  ```

  - 이유 : «가까이 가면 잘려요» 해결 글에서 near 를 0.01 로 낮추는 답이 흔함 · 즉시 보이는 실패(잘림·사라짐)만 회피
- **원인 (개념)**
  - 원근 투영 후 깊이 값은 **1/z 에 비례** → 깊이 정밀도가 가까운 곳에 몰리고 먼 곳은 성김 (비선형성)
  - 정밀도를 결정하는 값 = 1/near − 1/far → far 가 아니라 **near 가 지배** (near 0.01 → 1/near = 100)
  - 깊이 해상도 근사 : Δd ≈ d² × (1/n − 1/f) ÷ 2²⁴ (24비트 깊이 버퍼)
- **진단 도구**
  - far/near 비율 계산 · 200 m 지점 Δd 계산
  - 200 m 지점 바닥 위에 두께 0 인 면을 겹치고 카메라를 좌우로 흔들어 관찰
  - 대조 실험 : far 만 10000 → 200 으로 줄여 보기 → 증상 거의 그대로 → near 가 원인
- **수정 프롬프트**
  - 제약 : «nearClipPlane 0.1 이상 · farClipPlane / nearClipPlane ≤ 5,000 · 깊이 버퍼 24비트»
  - 검증 조건 : «200 m 지점 Δd 5 mm 이하» · «200 m 데칼, 카메라 5초 흔들기 → 깜빡이는 픽셀 0»
  - 손계산 : near 0.1 · far 500 · 200 m → 200² × 9.998 ÷ 2²⁴ ≈ 0.024 m = 24 mm → 불합격 · 5 mm 이하가 되려면 near ≥ 약 0.48
- **재발 방지 규칙** : `Camera near ≥ 0.1 · far/near ≤ 5,000 · 이유 : 깊이 정밀도는 near 가 지배 (#3)`

## #4 실시간 그림자 남발 · 감마/선형 색공간 혼동 (5주)

- **증상**
  - 에디터 Game 뷰 정상(60fps) → Quest 빌드에서 **프레임 급락** · 움직일 때 끊김
  - 라이트맵 베이크 후 색이 바래고 평평 · 밝은 영역이 한 덩어리 흰색으로 뭉침
  - 코드 오류·경고 없음 · 설정 값만의 문제
- **재현 프롬프트 예** : «실내 씬에 분위기 있는 조명 3개 배치해줘»
- **AI 가 흔히 내놓는 것**

  ```csharp
  light.type = LightType.Point;
  light.shadows = LightShadows.Soft;   // 광원 3개 모두 동일
  // Color Space : Gamma 그대로 · 베이크 미사용
  ```

- **원인 (개념)**
  - Unity 기본값 : 새 Point · Spot 광원은 그림자 꺼짐인 경우가 많은데(버전·파이프라인마다 다름) AI 코드가 광원마다 Soft 를 **명시**
  - 그림자맵 = 광원 자리에서 장면을 한 번 더 그린 거리 이미지 · Point = 6방향 → **6장** · 3개면 18장 + Directional 캐스케이드 최대 4장 = 그림자용 추가 그리기 최대 22회
  - VR = 두 눈 화면 → 픽셀 계산 2배
  - Color Space = Gamma 에서 PBR → PBR 값 범위는 **선형 계산 전제** → 조명 덧셈 과장 (sRGB 0.5 는 실제 빛 약 0.22 : 0.5^2.2 ≈ 0.22)
  - 데이터 텍스처(smoothness · metallic · occlusion)에 sRGB 체크 → 숫자가 변형된 채 계산
- **진단 도구**

  | 확인 대상 | 도구 | 판정 기준 |
  |---|---|---|
  | 그림자 광원 수 | Light 컴포넌트 일괄 확인 · 로그 | VR 기준 0~1개 |
  | 그림자 패스 | Frame Debugger | 그림자 그리기 단계 수 |
  | 색공간 | Project Settings → Player → Color Space | Linear |
  | 텍스처 | Inspector | albedo = sRGB 켬 · 데이터맵 = 끔 |
  | 프레임타임 | OVR Metrics Tool (헤드셋) | 11.1 ms 이내 |

- **수정 프롬프트**
  - 제약 : «Color Space = Linear · 실시간 그림자는 Directional 1개만, 나머지 광원 Mode = Baked · albedo sRGB 50~243 · metallic 0 또는 1»
  - 검증 조건 : «그림자를 켠 광원 수 로그 출력, 1 이하» · «같은 카메라 경로에서 프레임타임 2개 비교 (ms)»
- **재발 방지 규칙** : `실시간 그림자 광원 최대 1개 · 나머지 Baked · Color Space = Linear · 이유 : 그림자맵 비용 · PBR 은 선형 전제 (#4)`

## #5 밉맵 비활성화 · 알파 블렌딩 남용 (6주)

- **증상**
  - 먼 바닥·담장에 물결 무늬(모아레) · 카메라가 조금만 움직여도 지글거림 — 스크린샷 한 장으로는 잘 안 보임
  - 나뭇잎 덤불·유리창의 앞뒤가 뒤바뀌어 보임 · 각도에 따라 순서가 툭툭 바뀜 · 잎 많은 곳에서 프레임 급락
- **재현 프롬프트 예** : «선명한 바둑판 바닥 텍스처 만들어줘» · «나뭇잎을 반투명하게 해줘»
- **AI 가 흔히 내놓는 것**

  ```csharp
  var tex = new Texture2D(1024, 1024, TextureFormat.RGBA32, false); // mipChain = false
  tex.filterMode = FilterMode.Point;                                 // «선명하게» 를 Point 로 해석
  mat.SetTextureScale("_BaseMap", new Vector2(50, 50));
  // 잎 · 울타리 · 유리 전부 Surface Type = Transparent
  ```

- **원인 (개념)**
  - 밉맵 = 텍스처의 단계별 축소판 · 끄면 먼 표면도 원본에서 한 점만 읽음 → 화면 픽셀보다 무늬가 촘촘 → 나이퀴스트 미달 → 앨리어싱
  - 알파 블렌딩 = 앞 색과 이미 그려진 뒤 색을 C = α·C앞 + (1 − α)·C뒤 로 섞기 → **순서가 결과를 바꿈** → 먼 것부터 그려야 함
  - 반투명은 깊이 버퍼에 기록하지 않음 → 물체 중심 거리 정렬만 가능 → 큰 면·교차한 면은 어떤 순서도 정답 아님
- **진단 도구**
  - Inspector · 미리보기 하단 정보 · `tex.mipmapCount` (3D 표면 텍스처는 1 보다 커야 함) · Filter Mode 에 Point 없음
  - Scene 뷰 Draw Mode → Mipmaps · 카메라를 천천히 앞뒤 이동하며 관찰 (정지 스크린샷 금지)
  - Frame Debugger 로 투명 그리기 순서 · 머티리얼 renderQueue ≥ 3000 개수
  - 헤드셋 OVR Metrics Tool : 잎 덤불 가까이에서도 11.1 ms 이내
- **수정 프롬프트**
  - 제약 : «텍스처 밉맵 켬 (new Texture2D(…, true) + Apply(true)) · filterMode = Trilinear · anisoLevel = 4» · «잎·울타리·철망 = Opaque + Alpha Clipping · 반투명은 유리만, 서로 교차 금지»
  - 검증 조건 : «카메라 이동 녹화에서 먼 바닥 반짝임 없음 (평균 회색으로 가라앉음)» · «투명 머티리얼 수 N 개 이하»
- **재발 방지 규칙** : `3D 표면 텍스처 밉맵 켬 · Point 필터 금지 · 구멍만 필요하면 Alpha Clip · 이유 : 앨리어싱 · 반투명 정렬 불가 (#5)`

## #6 Transform 직접 이동으로 Rigidbody 무력화 (7주)

- **증상**
  - 천천히 걸을 때 : 정상처럼 보임
  - 벽에 밀어붙이면 부들부들 떨림 · 대시(빠른 이동)하면 얇은 벽 통과 · 다른 공과 부딪혀도 상대가 안 밀림
  - deltaTime(#2)까지 챙긴 코드 → «프레임 독립성은 맞는데 물리가 틀린» 두 번째 층
- **재현 프롬프트 예** : «WASD 로 움직이는 공 만들어 줘» (Rigidbody 가 붙은 공)
- **AI 가 흔히 내놓는 것**

  ```csharp
  void Update() {
      Vector3 dir = new Vector3(input.x, 0, input.y);
      transform.position += dir * speed * Time.deltaTime;
  }
  // Collision Detection : Discrete · Interpolate : None
  ```

- **원인 (개념)**
  - `transform.position` 대입 = **순간이동** · Rigidbody 속도(linearVelocity)는 0 그대로 → 물리 엔진은 «부딪힘» 이 아니라 «겹쳐 있음» 으로 처리 → 밀어내기만
  - 속도 정보 없음 → 상대에게 전할 운동량 없음
  - Update(화면 시계)에서 이동 → 고정 타임스텝(기본 0.02초) 물리 스텝 사이에 여러 번 순간이동 → 경로 검사(CCD) 무의미
  - 떨림 손계산 : 6 m/s · 90fps → 프레임당 6 ÷ 90 ≈ 0.067 m 파고듦 → 엔진이 밀어냄 → 다시 파고듦 반복
- **진단 도구**

  | 확인 대상 | 방법 | 판정 |
  |---|---|---|
  | 위치 대입 코드 | `transform.position` · `transform.Translate` 검색 | Rigidbody 달린 물체에 있으면 의심 |
  | 이동 위치 | Update 인가 FixedUpdate 인가 | Rigidbody 이동은 FixedUpdate |
  | 속도 값 | 실행 중 Rigidbody Info 의 속도 | 움직이는데 0 → 순간이동 |
  | 벽 통과 | 같은 속도로 20회 발사 (스타터 WallPassTest) | 통과 0회 |
  | Collision Detection | 빠른 물체의 모드 | v × Δt > 벽 + 크기 이면 Continuous 계열 |

- **수정 프롬프트**
  - 제약 : «입력은 Update 에서 읽고, 물리 적용은 FixedUpdate 에서 rb.linearVelocity 로 (중력 성분 유지)» · «Collision Detection = Continuous Dynamic · Interpolate = Interpolate»
  - 검증 조건 : «최고 속도로 같은 벽에 20회(또는 100회) 돌진 시 통과 0회»
  - 참고 : `rb.MovePosition` 은 Kinematic 물체(엘리베이터·문)용 · 자기 자신은 벽에 막히지 않음
- **재발 방지 규칙** : `Rigidbody 물체는 transform 직접 이동 금지 → FixedUpdate 에서 linearVelocity/AddForce (Kinematic 은 MovePosition) · 이유 : 물리 엔진의 속도 정보 소실 (#6)`
- **버전 주의** : Unity 6 에서 `Rigidbody.velocity` → `linearVelocity` 로 이름 변경 · AI 가 옛 이름을 쓰면 사용 중단(obsolete) 경고

## #7 Screen Space Overlay 캔버스 (10주)

- **증상**

- **진단 도구**

  | 확인 대상 | 위치 | 판정 기준 |
  |---|---|---|
  | Render Mode | Canvas 인스펙터 | World Space |
  | 크기 단위 | Canvas RectTransform Scale | 약 0.001 (캔버스 1 = 1 mm) |
  | 배치 거리 | Canvas 위치 ↔ 카메라 | 패널형 약 1~1.5 m · 눈높이 근처 |
  | 레이캐스터 | Canvas 컴포넌트 | Tracked Device Graphic Raycaster |
  | 입력 모듈 | EventSystem | XR UI Input Module · 씬에 EventSystem 1개 |

- **수정 프롬프트** : «World Space 캔버스, 눈높이, 1.5 m 앞, 폭 0.6 m · Scale 0.001 · Tracked Device Graphic Raycaster · EventSystem 은 XR UI Input Module» · 계속 필요한 정보는 손목 또는 Lazy Follow
- **재발 방지 규칙** : `VR 씬의 Canvas 는 World Space 만 · Overlay/Camera 모드 금지 · Tracked Device Graphic Raycaster 필수 · 이유 : 헤드셋에는 덧그릴 «화면 한 장» 이 없음 (#7)`

## #8 카메라 Transform 직접 조작 (11주)

- **증상**
  - 요청 : «A 버튼을 누르면 다음 관찰 지점으로 시점 이동하는 스크립트 만들어줘»
  - 에디터(헤드셋 없이) : 정상 이동 → 통과로 착각
  - 헤드셋 : 버튼을 눌러도 제자리 · 또는 한 순간 깜빡이고 원위치
  - AI 의 2차 수정(Tracked Pose Driver 끄기 · LateUpdate 덮어쓰기) → 고개를 돌려도 세상이 따라 돎 · 덜덜 떨림 → 몇 초 안에 멀미
- **재현 프롬프트 예** : 위 요청 그대로
- **AI 가 흔히 내놓는 것**

  ```csharp
  var cam = Camera.main.transform;
  cam.position = spot.position + Vector3.up * 1.6f;   // 눈높이를 코드에 박음
  cam.rotation = spot.rotation;
  ```

- **원인 (개념)**
  - Main Camera 의 Tracked Pose Driver 가 헤드셋 자세를 카메라에 기록 (기본 갱신 시점 Update and Before Render) → 내 스크립트가 쓴 값을 **렌더 직전에 다시 덮어씀**
  - 에디터에서 정상인 이유 : 헤드셋이 없으면 받을 자세가 없음 → 덮어쓰기 없음
  - 트래킹을 끄면 → 전정계는 회전을 느끼는데 화면은 정지 → 최악의 감각 충돌
  - XR 리그 구조 : `XR Origin → Camera Offset → Main Camera` · 이동은 리그(XR Origin)가, 머리 자세는 트래킹이 담당
- **진단 도구**
  - 코드에서 `Camera.main.transform` · `mainCamera.transform.position =` 검색 → 카메라에 쓰기 = 함정
  - Update 에서 쓴 값과 LateUpdate 값을 로그로 비교 → 다르면 덮어쓰기 중
  - Tracked Pose Driver 활성 여부 · Tracking Type (꺼짐 · Rotation Only = 2차 함정)
  - 리그 이동 버전과 같은 경로를 헤드셋에서 체감 비교
- **수정 프롬프트** : «Main Camera 의 Transform 은 읽기 전용 · 이동은 Teleportation Provider 에 TeleportRequest 로 요청 (XR Origin 루트 이동) · 회전은 Snap Turn Provider · 눈높이는 트래킹 원점 Floor 모드의 실측값»
- **재발 방지 규칙** : `Main Camera Transform 쓰기 금지 → XR Origin(Teleportation/Snap Turn Provider) 이동 · 이유 : 트래킹이 매 프레임 덮어씀 · 감각 충돌 (#8)`

## #9 부드러운 가속 이동 (12주)

- **증상**
  - 프롬프트 : «VR 에서 스틱으로 자연스럽고 부드럽게 이동하게 해줘»
  - 코드 깔끔 · 오류 없음 · 에디터에서 «고급 게임 같은» 출발·정지
  - 헤드셋 : 체험자 다수가 1~3분 안에 속 울렁거림 · 일부 중단 · 개발자 본인은 괜찮음 → «사람마다 다르지» 로 넘어가기 쉬움
- **재현 프롬프트 예** : 위 요청 그대로
- **AI 가 흔히 내놓는 것**

  ```csharp
  Vector3 target = MoveDir() * 4f;                                   // 최고 4 m/s
  vel = Vector3.SmoothDamp(vel, target, ref velRate, 0.8f);           // 0.8초에 걸쳐 가속·감속
  rig.position += vel * Time.deltaTime;
  rig.Rotate(0f, TurnInput() * 90f * Time.deltaTime, 0f);             // 부드러운 회전 90°/s
  ```

- **원인 (개념)**
  - 전정계(속귀)는 **가속에 반응, 등속에는 무반응** → 화면은 가속하는데 몸은 정지 = 전정-시각 충돌 최대 구간
  - 모니터 게임의 «좋은 손맛» = 가속·감속 곡선 → VR 에서는 그 곡선 구간이 바로 멀미 구간
  - 손계산 : 0 → 4 m/s 를 약 0.8초 → 평균 약 5 m/s² · 한 연구의 전방 가속 임계 평균 0.70 m/s² 의 약 7배 · 회전 90°/s = 요 회전 임계 평균 27.1°/s 의 약 3.3배 (Terenzi & Zaal 2020 · 참가자 18명 · 개인차 큼)
- **진단 도구**
  - 같은 경로 · 같은 시간 상한(3분)에서 세 방식 비교 : A 부드러운 가속(원본) · B 등속·즉시 전환(1.2 m/s, 스냅 턴 22.5°) · C 텔레포트
  - 기록 : SSQ 전후 변화량 · 체험 지속 시간(중단 시점) · 로그 최대 가속도(이번 프레임 속도 − 지난 프레임 속도 ÷ deltaTime)
  - 판정 : 체감 «괜찮다» 가 아니라 로그 수치 + SSQ 변화량 · 2~3명 결과는 경향으로만
  - 안전 : 동의자만 · 앉아서 · 멀미 씬 노출 최대 3분 · 언제든 중단
- **수정 프롬프트** : «VR 컴포트 기준 이동 · 가속 곡선 금지 · 입력 즉시 등속 1.2 m/s · 놓으면 즉시 정지 · 스냅 턴 22.5° (쿨다운 0.25초) · 이동 중 베그넷 · 텔레포트 옵션» · 검증 조건 «로그상 가속 구간 ≤ 1프레임»
- **재발 방지 규칙** : `이동에 SmoothDamp/Lerp 가속 곡선 금지 → 즉시 등속 · 회전은 스냅 턴 · 이유 : 가속 = 전정-시각 충돌 (#9)`

## #10 에디터 기준 최적화 (14주)

- **증상**
  - «90fps 로 최적화해 줘» → AI 수정 · 에디터 Game 뷰 Stats 120fps 이상 → «완료»
  - Quest 빌드 : 60fps 이하 · 고개 돌릴 때 덜컥 · OVR Metrics 에 스테일 프레임(새로 그리지 못한 프레임) 누적
  - AI 수정 중 일부는 실제 병목과 무관 (CPU 스크립트 정리 ↔ 실제 병목은 GPU 후처리)
- **재현 프롬프트 예** : «씬을 90fps 로 최적화해 줘. 에디터에서 지금 75fps 나와.»
- **원인 (개념)**
  - 같은 씬, 다른 기계 : 에디터 Game 뷰 1280×720 ≈ 92만 픽셀 vs Quest 3 2064×2208×2 ≈ 911만 픽셀 → 약 9.9배 · 계산 능력은 몇 분의 1
  - 타일 기반 GPU : 화면 전체를 메모리에 썼다 다시 읽는 작업(후처리 · Depth/Opaque Texture · HDR)이 비쌈
  - 발열·클럭 단계 조정 → 처음 1분과 10분 후 수치가 다를 수 있음
  - AI 는 헤드셋을 볼 수 없음 → 병목 위치를 모른 채 «일반 최적화 목록» 적용
- **진단 도구**

  | 관찰 (헤드셋 실측) | 판정 | 의심할 곳 |
  |---|---|---|
  | OVR Metrics GPU 사용률이 계속 최대 근처 · fps 낮음 | GPU 병목 | 후처리 · 오버드로 · 실시간 그림자 · 무거운 셰이더 · 해상도 |
  | GPU 여유 · Profiler CPU 메인 스레드 11.1 ms 근처 이상 | CPU 병목 | 드로우콜 · Update 속 검색 · 물리 · 가비지 생성 |
  | 평소 정상 · 특정 순간만 튐 | 순간 부하 | Instantiate · 에셋 로드 · 가비지 컬렉션 · 첫 셰이더 사용 |

- **수정 프롬프트**

  ```
  [측정] Quest 3 · 배포 빌드 · OVR Metrics : 평균 58fps · GPU 사용률 최대 근처 · Profiler CPU 메인 7 ms
  [판정] GPU 병목
  [요청] URP Asset 에서 GPU 비용 큰 설정 후보 3개를 비용 큰 순으로 · 각각 끄면 사라지는 시각 효과 설명
  [검증 조건] 헤드셋 실측 평균·최저 fps 와 스테일 프레임 수를 수정 전후로 기록
  [비목표] 스크립트 수정
  ```

- **재발 방지 규칙** : `성능 판정은 헤드셋 실측(OVR Metrics · 배포 빌드)만 · 병목 판정 전 최적화 금지 · 이유 : 에디터와 온디바이스는 다른 기계 (#10)`
